# Records for the two attribution controls (RSIBridge discussion #6029)

These are the records @GBX-Max1220 asked for, following the [earlier summary of the two cases](https://github.com/bytedance/deer-flow/discussions/6029#discussioncomment-19149562) in discussion #6029:

- **A. Meeting-note parser:** the unchanged outputs, and the scoring logic before and after the parser fix.
- **B. Shortened evaluator input:** the actual evaluator input, and how it was constructed.

Neither replay makes a model or provider call. The run numbers and figures match the earlier summary and its per-run CSV.

## A. Meeting-note parser (`A-minutes-parser/`)

| Path | What it is |
| --- | --- |
| `outputs/Run1` … `outputs/Run8` | The eight saved final output sets as the agent wrote them: 60 meeting notes plus `minutes/index.md` each; Run7 also wrote an `actions-tracker.md`. One line is masked, see below |
| `source/en`, `source/zh` | The 60 source meetings per language. They are synthetic, generated by a seeded script for this benchmark; no real people or data |
| `expected/` | The registered facts per meeting: title, date, attendees, decision token, and each action's owner, task and due date |
| `scoring/legacy_minutes_rules.py` | **Before:** the four historical scoring functions, copied verbatim. They include the N−1 tolerance and the index parser that reads the first date-bearing line |
| `scoring/minutes_strict.py` | **After:** the fixed scorer, `minutes-strict-v1`, unchanged. Its `legacy_score_minutes()` runs the historical functions by AST, so both rule sets see the same files |
| `scoring/test_minutes_strict.py` | The 17 scorer tests. Only three path lines differ from the original, to point at this layout |
| `recorded-scores.json` | The score each set got when it was recorded |
| `regrade.py` | Runs both rule sets over the eight sets and prints each historical misread |

Run it with Python 3.9 or later; it uses the standard library only:

```sh
cd A-minutes-parser
python regrade.py --json regrade-results.json
python -m unittest discover -s scoring -p "test_minutes_strict.py"
```

Expected output:

```
run   lang recorded historical  fixed  historical misreads
Run1  en        5/5        5/5    5/5  0
Run2  en        5/5        5/5    5/5  0
Run3  en        5/5        5/5    5/5  0
Run4  zh        4/5        4/5    5/5  2
Run5  zh        5/5        5/5    5/5  0
Run6  zh        4/5        4/5    5/5  2
Run7  en        4/5        4/5    5/5  3
Run8  zh        4/5        4/5    5/5  2
```

The historical rules reproduce every recorded score. The four failing sets all fail one check, the index action counts. For each meeting, the historical parser takes the first line in `index.md` that contains the meeting's date, and reads its last number as the action count. In these sets, that first line is a summary above the table rather than the meeting's row:

- a coverage line such as `统计范围：2026-07-01 至 2026-09-27，共 60 次会议。`, read as 60 actions for the first and last meetings;
- a period line with no number, so no count is read;
- in Run7, a line containing a local file path that happens to include the date `2026-09-06`, the date of one meeting. That misread comes from the environment, not from the agent's work.

With N−1 tolerance, one misread passes; two or three fail the check. `regrade.py --json` lists every misread: the line the historical parser used, the numbers it read, the expected count, and the actual table row.

**One masked line.** Line 3 of `outputs/Run7/minutes/index.md` contained a local file path. It is replaced with `<local path, redacted, 2026-09-06>`, keeping only the date the parser matched. Every score and misread is identical before and after the edit. Nothing else in the outputs is changed.

The fixed scorer reads one table row per meeting, and finds all 60 rows and exact counts in every set. It also removes the N−1 tolerance and checks more facts, so it is stricter elsewhere; the tests include single-defect controls for that. Its 8/8 covers the registered facts and structure only. For example, an optional prose total in Run6 says 175 actions where the source has 177; no check covers that sentence.

## B. Shortened evaluator input (`B-evaluator-input/`)

| Path | What it is |
| --- | --- |
| `observed-A-deepseek.evaluator-input.json`, `observed-B-glm.evaluator-input.json` | The exact messages (system and user) the Goal evaluator received after each run's first turn |
| `inputs/*.formatter-input.json` | What the evaluator function was given: the initial Goal and the three first-turn messages (a hidden date reminder, the 10,375-character user message, the answer) |
| `boundary-12000…`, `boundary-12001.evaluator-input.json` | The DeepSeek answer padded with internal spaces only, to just under and just over the cap |
| `historical-verdicts.json` | What each evaluator actually returned during the run, with ids and timestamps removed |
| `replay_evaluator_input.py`, `replay-results.json` | The rebuild script and its output |

**How the input is constructed.** The worker passes the checkpoint's messages to `evaluate_goal_completion()` in `runtime/goal.py`. That calls `format_visible_conversation()`, which drops the hidden reminder, builds `User:` and `Assistant:` lines, and caps them at 12,000 characters in `_cap_evidence()`. Lines are kept whole from the end. If the latest user line does not fit, it is kept at the top but cut to 2,000 characters. The capped text goes into the user message under "Visible conversation evidence", after the Goal objective; the system message holds the evaluator instructions.

In case B the two lines total 12,127 characters, 127 over the cap. So the user line is cut to its first 1,994 characters, followed by `... [8381 more chars]`. Document 5 starts at character 3,694, so it is gone, and 8,233 characters of the budget stay unused. The GLM evaluator then wrote that "Document 5's content is not visible anywhere in the evidence" and returned `missing_evidence`. **The evidence was absent from what it received, not ignored.** In case A the two lines total 11,953 characters, so nothing is cut and Document 5 is present. The DeepSeek evaluator returned achieved. The two answers differ, so the two verdicts alone do not show what truncation does to a verdict. The boundary pair holds the answer fixed: one extra space moves the evidence from 12,000 to 12,001 characters, and the conversation evidence the evaluator receives drops to 3,641 characters, without Document 5.

**How these files were made.** `replay_evaluator_input.py` calls DeerFlow's unchanged `evaluate_goal_completion()` at commit `505c33c793389451f2ce7183bdbd4f3465f22f66`. The stand-in model records the messages passed to it and stops, so there is no provider call. The observed inputs are therefore rebuilt, not captured on the wire. The script checks that it rebuilds both published inputs byte for byte. The formatter inputs are the stored first-turn state, reduced to the fields the formatter reads:

- message ids are replaced;
- run ids, timestamps (including the Goal's), provider metadata and the models' hidden reasoning are removed.

None of these reach the evaluator. PII redaction was off in both runs, the default, so it does not explain the loss.

```sh
git clone https://github.com/bytedance/deer-flow && git -C deer-flow checkout 505c33c793389451f2ce7183bdbd4f3465f22f66
# Use a Python environment with that checkout's backend dependencies.
python B-evaluator-input/replay_evaluator_input.py --deerflow-src deer-flow --out rebuilt
```

Expected output:

```
observed-A-deepseek    evidence  11953 ->  11953 unused    47  Document 5 kept: True  matches published: True
observed-B-glm         evidence  12127 ->   3767 unused  8233  Document 5 kept: False  matches published: True
boundary-12000         evidence  12000 ->  12000 unused     0  Document 5 kept: True
boundary-12001         evidence  12001 ->   3641 unused  8359  Document 5 kept: False
```

This is pinned to the code at the time. DeerFlow #7345, merged on 2026-10-23, changed the allocation so that spare room restores a shortened user line. No fuller-evidence verdict was generated here, so these records do not show how the evaluator would decide with Document 5 restored.
